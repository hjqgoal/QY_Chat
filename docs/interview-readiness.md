## 结论

可以作为实习面试项目展示，但不能称为“所有功能在所有情况下正确”或“生产级服务”。离线工程回归通过，人工校对后的真实生成、后台评估和记忆保存已完成联调；**当前视觉模型尚未通过这次合成截图验收**。现场优先展示文字背景入口，截图入口必须校对，并准备识别失败的备用路径。

本次未更换真实 `.env` 中的模型、未提交密钥、未修改个人聊天数据库。真实调用经用户许可，仅发送合成内容，使用自动销毁的临时 SQLite 数据库；产生了少量模型调用费用。

### 实际识别问题

合成图片只有三句：对方“今晚一起打游戏吗”，我“我已经约了别人，今晚来不了”，对方“好，那下次吧”。文字清晰，左右分列。第一次错误归属导致主题也跟着出错。后续人工按已知原文纠正后，主题为：

> 朋友邀请今晚打游戏，用户因已有安排拒绝，对方表示下次再约，当前只需礼貌收尾。

这说明校对输入会影响下游，但不能证明模型对其他场景都正确。程序不会用“双方必须交替说话”的假设强行修正，真实聊天完全可能连续由同一人发送。

官方能力表标明当前 `qwen3.5-ocr` 不支持结构化输出，不能通过强加 JSON Schema 参数假定解决问题。它能否在提示要求下稳定给出聊天角色和格式，需要专门评测。[阿里云模型说明](https://help.aliyun.com/zh/model-studio/qwen3-5-ocr)

### 耗时的正确解释

两次短对话首次生成分别观测到 57.29 秒和 26.11 秒，后台评估分别约 41.75 秒和 38.82 秒。样本少、输入也有校对差异，**不是优化前后对照，不代表延迟降低了某个百分比**。第一次返回不含后台评估、记忆的完成等待；高风险场景页面会等待评估再展示候选。异步化减少了串行阻塞，不会让模型推理本身变快，也不保证调用费用下降。

## 目前架构怎么讲

```text
截图 / 文字背景
  -> 文件校验 -> 视觉识别 -> 人工确认文字与说话人
  -> 联系人记忆检索 + 关系 Skill + 本人风格证据
  -> 强模型一次理解与生成（按需调用天气 MCP）
  -> 三条候选 + 时机/策略 + 耗时信息
  -> 后台独立评估 -> 必要时一次修订 + 一次复评
  -> SQLite 记忆任务 -> 联系人摘要、对话事件、本人风格
```

- 后端 FastAPI + Pydantic + SQLAlchemy；数据持久化在 SQLite；前端原生 HTML/JavaScript。
- 当前是显式 Python 服务编排，不是 LangGraph；模型角色可独立配置，不等于训练了多个 Agent。生成和评审目前用同一型号的独立调用，存在相关偏差。
- 关系规则实际加载 `SKILL.md` 正文和 YAML 参考规则。本人风格来自确认后的本人消息与反馈，不是微调训练。
- 长期事件按 `user_id + contact_id` 隔离，先取最近 60 条候选，再用相似度乘时间衰减排序，默认选最多 3 条。衰减是按场景可配置半衰期的指数衰减。
- 支持 embedding 语义检索和词面降级；10 月 22 日检查时缺少本地依赖，10 月 23 日已改为远程千问原生向量 API 并完成真实验证。没有独立向量数据库，也没有全量历史向量索引。
- 记忆任务通过 SQLite 持久化，执行时使用独立数据库会话，事务保证更新一致，删除后迟到结果不能重新写回；质量任务在进程内存中，重启会丢失。
- MCP 是工具协议和服务边界；天气工具不应凭模型记忆报实时天气，城市不明确应澄清，接口失败不能编造数据。

## 演示步骤

1. 先展示真实需求和产品边界：只辅助回复，不自动发送，不侵入微信；情绪分析是可能解释，不是心理诊断。
2. 用以下合成背景走文字入口，选择“朋友”，先展示三条候选、主题和诊断；等待模型期间讲解上述流程。
3. 展示后台评估与编辑保护：修改一条候选，旧评价失效，不会用迟到评估覆盖用户文字。评价是辅助意见，不展示未经校准的百分制保证。
4. 用合成截图展示校对。识别失败就展示明确错误并回到文字入口；识别成功也核对“我/对方”，不要把预设答案冒充识别结果。
5. 在独立演示数据库保存一次记忆，再展示记忆管理和反馈。待后台任务完成后再查，不把“排队中”讲成“已保存”。

## 面试前的优先级

1. **P1：视觉提取稳定性。** 用合成/获得授权的截图建立独立验收集，覆盖连续同侧、重复文字、深浅主题、长气泡、长截图、系统通知。对比支持聊天布局提取的视觉模型，分别量化文本与说话人错误率；不要只按 OCR 文字能力选型。本次未擅自更换 `.env`。
2. **P1：时延与评估成本。** 固定输入与网络，记录生成、工具、评审、修订、记忆的耗时和用量；积累样本后才算 P50/P95。对提示长度、模型角色和推理预算做对照，不能只凭一次快了就宣布优化有效。
3. **P1：人类偏好校准。** 把参与提示词调试的样例与保留集分开；用盲评对比自然度、事实/承诺边界、接话作用和候选差异。独立评审不是客观裁判，也不能证明对方一定满意。
4. **P2：语义检索质量与索引。** 10 月 23 日已启用并验证远程 embedding；后续可对比词面方案的召回质量、费用、隐私和延迟。历史规模扩大后考虑持久化向量和索引，而不是每次重新编码候选。
5. **公网前必须完成：** 身份认证、授权隔离、限流、代理层上传限制、保密存储/备份/删除策略、持久化质量队列和可观测性。当前 `user_id` 是客户端提供的本地命名空间，**不是身份认证**；单进程线程队列不是分布式系统，不要直接绑定公网。

## 可以说与不能说

可以说：实现了带人工校对、关系规则、检索记忆、受控工具调用和异步质量反馈的本地聊天辅助原型，并用隔离数据回归失败路径。

不能说：100% 情绪理解、所有回复都高情商、模型评分客观、稳定秒回、万人并发、完整生产级多 Agent 系统，或离线测试通过代表真实模型准确率 100%。语义向量 RAG 已于 10 月 23 日通过真实小样本验收，可如实介绍，但不能据此宣称全场景召回准确。

被问“为什么不直接套框架”时，说明当前流程较固定，显式编排便于控制调用次数、错误与事务边界；若后续需要持久化复杂状态图、多分支恢复与跨节点中断，再评估 LangGraph 等框架。框架可以改善编排能力，不能自动修好 OCR、情绪误判或推理延迟。
