# 评估可用性与分级提速验收

日期：2026-10-23。目录：`/Users/jiaqihong/Desktop/QY_Chat`；环境：conda `my_demo1`。

## 这次解决什么

此前页面突出的是整组“待确认”，五维判断没有直接显示；普通未知与关键缺失共用一个列表，容易出现等了很久却只看到“信息不足”。所有场景还使用相同评审提示和推理预算。

现在每条已验证的原文评价显示：

- 五维 1-5 档：说话自然度、接话与立场、关系分寸、情境与情绪、本人风格。无法判断填 null，页面显示“暂不计分”，不是零分。
- 具体判断与需要调整的问题；详细证据可展开。已发现的明确问题不被同时存在的未知信息盖住。
- 关键缺失（会影响这句话是否合适）与普通提醒（不阻止使用）分开。例如未知目的地影响天气建议；没有本人风格样本只影响风格项，无法保证对方反应不应单独否定所有候选。
- 整组统计：有效评估几条、可用几条、待调整几条、需要补充信息几条。保留候选差异的具体理由，不用固定文案替换。
- 仅从全部评价已通过格式和原文校验的候选组中，选出其中“基本可用”的候选作优先参考。先比较四个核心维度的最低档，再比较合计；并列就并列。不参考生成者的自夸理由，也不声称是唯一最佳。

仍不展示在线百分制总分。五档、结论及推荐都未经人类偏好校准，不是情商准确率或对方满意概率；不能要求每轮一定给出一个高分答案。

## 流程与成本

1. 强模型生成三条候选，生成模型与生成预算不变。
2. 服务端根据分析、场景、控制选项、说话人/校对状态和天气依据选择评审模式。低风险走精简；中高风险、冲突、边界、道歉、明确拒绝/降温、识别需复核、未知说话人或天气依据走完整。
3. 精简使用短版准则、较短证据和较小推理预算，但仍评价全部三条、全部五维及候选组差异，使用同一原文绑定协议和验证规则。它不是跳过评审或本地规则伪装成模型评估。
4. 手动“详细评估当前回复”始终完整。不同模式的请求不会被合并为同一任务。
5. 具体缺陷仍可触发既有的一次定向修订与完整复评；缺少信息不自动当作低分。部分结构无效时保留有效单条结果，不自动修订、不发布整组推荐。
6. 原稿不会被轮询覆盖；编辑、改上下文、取消或重评后旧推荐失效，过期任务不套用到新文本。

首次评审通常一次模型请求。若进入修订与复评，整体最多三次，不应将首轮约24秒宣传成全部流程约24秒。当前轮询仍在整项任务结束后展示最终报告。

## 配置

真实 `.env` 未修改。以下默认值已由代码生效，`.env.example` 只是模板，不是运行时配置：

```dotenv
QUALITY_QUICK_ENABLED=true
QUALITY_QUICK_THINKING_BUDGET=512
QUALITY_QUICK_MAX_COMPLETION_TOKENS=3072
QUALITY_THINKING_BUDGET=2048
QUALITY_MAX_COMPLETION_TOKENS=6144
```

设 `QUALITY_QUICK_ENABLED=false` 并重启可让自动评审恢复全部完整模式。推理/输出参数仅发给适配的百炼模型系列，其他兼容服务不发送专有字段；诊断记录请求预算与实际用量，未发送时预算为 null。阶段超时、队列和总流程预算沿用原值。

无需新增环境、依赖或数据库迁移。重启现有服务，浏览器刷新后重新生成/评估；已结束的旧任务不会自动重算。OCR 首选与备用策略、Embedding、记忆存储均未改动。

## 验证结果

- 290 项后端离线测试通过，其中新增12项覆盖提醒/关键未知、评分缺失、具体问题优先、推荐排序、部分失败、路由和预算隔离。生成、记忆、天气、OCR 的既有回归也通过；离线测试不调用付费模型。
- 四组前端脚本通过；1280px、390px 真实浏览器检查通过：可见五档、空分显示、转义、人工编辑、旧推荐失效、取消、修订采用、超时与部分结果、OCR 校对和无横向溢出。
- 真实验证仅发送合成文字，不读取个人数据库、不发送用户截图，不更换密钥或模型。评审模型仍是已配置的 `qwen3.8-max`。

这些时间是单次只读服务调用，含接口往返，不含排队、生成、修订与复评；不是均值、P95 或稳定性基准。日常对照发生在最终“具体问题优先于未知”排序调整前，原报告将候选2记为 uncertain；最终规则会优先显示建议调整，同时仍保留其关键未知，排序变化有离线回归覆盖。没有为得到好看的统计重复调用直到全绿。

初次失败后加强 JSON Schema 的非空文本/列表数量限制，明确无问题必须 `[]`，不能 `['']`。未放松本地校验或填默认高分。上游仍可能返回不合格的结构或不够充分的证据，不能承诺100%有效。

## 仍然存在的限制

- 完整评审本次仍约60秒；你此前的恋人冲突案例仍走完整模式，不能承诺大幅提速。
- 精简降低推理预算可能影响细微判断。路由依赖生成阶段分析，存在误分场景的风险；仍保留手动完整评估。
- 生成与评审目前是同一个模型的独立请求，并非独立训练、无偏的裁判。两种模式对档位和候选差异可能意见不同；本次也观察到部分依据表达不完整。结构合规不等于语义正确。
- 优先参考是透明规则排序，不是学习到的个人偏好排名；少量合成反例通过不代表对真实聊天全面可靠。
- 评估任务保存在内存，重启会丢失。原稿仍需用户选择和确认，不自动发消息。
